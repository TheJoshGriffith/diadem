# Running Diadem on Unraid

Deployment files for running Diadem in a container against an existing
Golbat/Dragonite/Koji stack. Everything here lives on the `deploy` branch so
`main` stays a clean tracking clone of upstream.

## Why this replaces the root Dockerfile

`setup.sh` **hard-links** `config/config.toml` to `src/lib/server/config.toml`,
and the built app reads the second path. A bind mount over either path does not
update the other, because a hard link cannot span a mount point. The root
Dockerfile (yours, never part of upstream) therefore bakes config into the image,
and changing any setting means rebuilding it.

`entrypoint.sh` resolves config at container start instead: it takes a mounted
file or the baked example, overlays environment variables onto it, then *copies*
(never links) the result into both locations before starting the app.

## Configuration

Any config path can be set with a `DIADEM__` variable. `__` separates segments,
and segments match case-insensitively against the base file, so `INTERNALDB`
finds `internalDb`:

    DIADEM__SERVER__DB__HOST=mariadb
    DIADEM__SERVER__INTERNALDB__PASSWORD=...
    DIADEM__SERVER__GOLBAT__URL=http://golbat:9001
    DIADEM__CLIENT__GENERAL__MAPNAME=Harris Map

Values coerce: `true`/`false` to boolean, digits to number, anything else to
string. For arrays and tables, prefix with `json:`

    DIADEM__SERVER__PERMISSIONS='json:[{"everyone":true,"features":["gym"]}]'

The array-heavy sections (`mapStyles`, `uiconSets`, `permissions`) are far more
readable in TOML. Leave them in a file mounted at `/config/config.toml`, or pass
a whole base file as `DIADEM_CONFIG_TOML_B64`.

## Order of operations

1. `bash deploy/bootstrap-db.sh` on Harris — creates the `diadem` database, an
   owner user for it, and a read-only user on `golbat`. Prints the four
   variables you need.
2. Fork the repo, push this branch, let the workflow publish to GHCR.
3. Create the container from `deploy/unraid-template.xml`.

## Networking

Container-name DNS only works on a user-defined Docker network, not Unraid's
default `bridge`. Create one and attach the stack:

    docker network create pogo
    # then set Network Type: pogo on mariadb, golbat, dragonite, koji,
    # nginx-proxy-manager and diadem

Diadem can then reach `mariadb:3306`, `golbat:9001`, `dragonite:7272`,
`koji:8080` by name, Nginx Proxy Manager can reach `diadem:3000`, and no port
needs publishing to the LAN at all — including MariaDB's 3369, which can then
be removed.

If you'd rather not re-network the stack, point everything at `10.0.0.20` with
published ports instead. It works today with no changes, but keeps the database
exposed to your LAN.

## ORIGIN

`adapter-node` has no way to know its public URL, and SvelteKit refuses any POST
whose `Origin` header does not match. The rejection happens before routing, so
the symptom is 403s in the browser console with **nothing in the container
logs** - GETs keep working, which makes it look like a permissions problem.

Set `ORIGIN` to exactly how the browser reaches the app, including scheme and
port. Change it when you put a reverse proxy in front.

## Migrations

The image ships SQL generated by `drizzle-kit generate` at build time and applies
it on start with `drizzle-orm`'s migrator, so `drizzle-kit` isn't needed at
runtime. Set `DIADEM_AUTO_MIGRATE=false` to skip.

## Known risks

- `sharp` and `@node-rs/argon2` are native modules on musl. They publish musl
  builds, but they're the first thing to check if the image fails to start.
- `pnpm` is pinned to 10 rather than `latest`, since the lockfile is v9.0.
- The container runs as root, matching most Unraid images. Worth revisiting.
